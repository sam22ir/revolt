# Godot migration plan

## Status

- **Slice 0 done** (branch `godot-client`): Godot 4.7.2 + export templates installed (checksums verified), `apps/godot/` project, GUT tests (`pnpm godot:test`, 23 tests, works from a clean checkout), shared data export (`pnpm godot:export`), Web export (`pnpm godot:web`) served by the `godot-web` launch entry (port 4173 since slice 1) and checked in the built-in browser at phone size in `en` and `ar` (shaping and RTL mirroring correct).
- Font: **IBM Plex Sans Arabic** (Regular + Bold, SIL OFL, from google/fonts, in `apps/godot/fonts/`), set as the project default font; it covers Arabic and Latin. Plain IBM Plex Sans has no Arabic glyphs.
- **Slice 1: browser-verified, phone check pending** (57 GUT tests): guest session reused from `user://`, `GET /v1/map`, isometric ground as one mesh, region seams, bases, NPCs with level badges, HQs, march routes, pan/wheel/pinch camera, HUD that mirrors in Arabic while the map does not. Checked in the built-in browser at phone size in `en` and `ar` against the mock server: same geography in both, zoom and drag verified. Pinch is covered by unit tests only (the pane cannot send two-finger touch). Native build time of the map is ~50 ms (about 190 ms in the browser). The Android density path (`screen_get_scale`, used instead of `innerWidth` for the zoom scale) is unverified. **Phone check (needs the phone on USB):** `adb reverse tcp:4173 tcp:4173 && adb reverse tcp:8787 tcp:8787`, then open `http://localhost:4173` in Chrome on the phone (see `docs/device-testing.md`): check pinch, drag, Arabic, and how long "Loading the map…" lasts. The built-in browser pane only advances the page it has fronted (use `tabs_select`) and runs a Godot page at about 1 frame per second, so it cannot give performance numbers; it is good for layout, language and interaction.
- **What slice 1 does not have: the Phaser ground look.** A subagent outlined the Phaser map: the ground is not just `terrainAt`. It is baked from more seed-derived functions that each need a GDScript port with golden fixtures: `fertilityAt` and `geographyOf` (wadis, roads, oases; `packages/rules/src/geography.ts`), decor clusters (`scene/decor-clusters.ts`), decals (`world/ground-decals.ts`), props (`scene/terrain-props.ts`, whose `hash01` ignores the seed), ground tint (`world/ground-tint.ts`) and the road/wadi shaping in `world/feature-layer.ts`. Art: WebP atlases under `apps/client/public/art/terrain/` (decals, trees, rocks, peaks, scrub) and map sprites (`camp`, `outpost_*`, `marker_*`). Tile size 96x48 and the projection are already identical to Phaser's.
- **Slice 1b (ground look): ported and rendering, first pass; look not yet tuned.** Part A: hash01, fertility, clusters, geography (wadis, roads, oases), blended colours, props, decals and shaped road/wadi polylines all match the client's real pipeline tile for tile on four seeds including the mock server's (82 GUT tests). Part B: smooth colour field + wash, decals and props as `MultiMesh` batches (one draw call each, painter's order, occupied ring, hidden below zoom 0.4), roads/wadis/oases drawn in code, mask and rim. Checked in the built-in browser beside the Phaser client on the same seed, in en and ar: same geography, same layer order, similar style. **Native build time (headless, GDScript compute only, GPU uploads excluded): about 700 ms**: art load and pack 100, geography 245, ground plan 250, fertility and clusters 22, terrain and regions 23, feature shaping 21, ground layer 11, props 32. Expect two to four times that on a phone and in the browser. If it is felt on the phone, the fallback is to cache the per-seed results (geography, plan, shaped paths) in `user://` keyed by seed, size and a version number, so only the first launch pays; a worker thread is not an option for the no-thread web build. **Known differences from Phaser, to tune next:** decal density, alpha and kinds are exact (fixture-verified), so do not retune them; the green wash now uses Phaser's mottled grain (`ground_wash.gdshader`) and the runtime detail overlay is ported (`ground_detail.gd`, faded by zoom from 0.35 to 0.6, hidden with `?hide=detail`); the decal strength was not retuned, so compare the look again on the phone; region seams are still the slice-1 style (alpha 0.55, width 3, no far-zoom variant) where Phaser uses a softer 0.32 band and a faint line below zoom 0.3; objects (bases, NPCs, HQs) are still flat placeholders (their sprite art is a separate slice); the web build takes tens of seconds to start in this pane (about 1 frame per second there, so it says nothing about a phone). **Phone risk (the roads layer is fixed, see below):** the remaining per-frame cost is fill rate of the stacked full-map quads (colour field, wash, detail) and the decals; if a phone struggles, render the static ground layers into a texture once (SubViewport) or merge the wash into the field. Debug aid: `?hide=decals,props,wash,features,seams,objects,ground,detail` on the page URL hides layers. **Map frame cost, measured (headless Chromium, software GL, phone viewport; not a phone number):** the map screen submits about 11,600 draw calls and 300,000 objects (680,000 primitives) per frame and runs at about 1 fps there, against 51 draw calls and 145 objects on the base. Hiding only the roads, riverbeds and oases (`FeaturePainter`) drops it to 274 draw calls and 1,300 objects, so that layer is about 99.5% of the render load: every wadi and road is thousands of separate antialiased `draw_line` calls, two to three strokes per path plus round-join discs, all kept and re-rendered each frame. **Fixed:** `FeaturePainter` now builds the paths into one mesh with a surface per colour layer (triangle strips with per-point width and round caps, about 9 draw calls, edges not antialiased); a 64-tile map baked into a texture would have been too large for a phone. After the fix the same headless run shows 285 draw calls, 1,300 objects and 51,000 primitives on the map screen (from 11,630, 300,591 and 681,314), script time 13 ms (from 905 ms) and about 2.8 fps against 0.4 fps before. What remains there is fill rate in the software renderer (hiding the whole ground layer doubles the frames; hiding any one part barely changes them): the full-map colour field, wash and detail quads plus the decals. A real GPU should shrug that off, but only a phone can say, so the per-frame check on the phone is still open. Map load there takes about 2 s (base ready in 1 to 2 s, `map build` about 2 s), so the minutes seen in the built-in pane come from that pane being hidden, which throttles its frames to about one per second or fewer: **do not read performance from the pane.** Debug aid: `?debug=fps` prints fps, process time, draw calls and objects every 3 s to the console and `window.revoltLog`, times the base and map builds, and gives the page `window.revoltShow('base'|'map')` and `window.revoltHide(layer, hidden)`; headless Chromium (`agent-browser`) can drive it. **Grain textures are baked:** `apps/godot/art/ground/ground-grain.png` and `ground-detail.png` are made by `godot --headless --path apps/godot -s tools/bake_ground_grain.gd` (lossless import). The runtime only loads them; generating the detail texture in GDScript took about 1 s natively, too slow for a phone on each launch. `test_ground_grain.gd` fails if a PNG no longer matches the generator, so rerun the bake after changing `ground_grain.gd`.
- **Slice 2: session and network, browser-verified (live map), alliance socket covered by tests only.** `Session` (`scripts/session.gd`) holds the base and the server clock: every reply with `now` syncs the clock (a reply stamped up to 30 s behind the current estimate is an older answer that arrived late and is ignored, so counters never jump back), every reply with `state` replaces the base (unless it is stamped earlier than the reply that last set it, which is an older answer overtaken by a newer one, for example a `/v1/state` fetch that lands after an intent reply; the liberations follow the same rule), refreshes of `/v1/state` coalesce (one in flight, one follow-up, so a push after the answer is not lost), `send_intent` applies the base of a refused intent too, and a 401 mid-session only emits `auth_lost` (only the start-up check may create a guest, since a new guest replaces the base). `LiveSocket` (`scripts/net/live_socket.gd`) wraps `WebSocketPeer`: subprotocols `revolt.v1` and `auth.<token>` (token read on every connect), backoff 1, 2, 5, 10, 30 s reset by a well-formed frame, 15 s handshake timeout, 1 MiB inbound buffer (a snapshot is about 6 KB per 20 bases; the default is 64 KB), non-text and malformed frames dropped, URL derived from the API base (`http` to `ws`, so `?api=` keeps working). `MapMessages` and `AllianceMessages` port the client's frame parsers. `WorldMap.apply_snapshot` swaps bases, NPCs, HQs and marches in place and never rebuilds the ground for the same seed and size; seams are rebuilt only when the liberated regions changed, props only when the occupied tiles changed, and a snapshot that arrives during a build waits (only the latest is kept). The map socket starts after the first build; the alliance socket follows the membership (since chunk D: it starts when the player is in an alliance, restarts for another one, and stops when they are in none, including after `kicked`). On Android resume the state is refreshed and a dead socket reconnects (an open one is left alone). Debug aid: `?debug=net` prints socket events to the browser console. **Verified in the built-in browser** against the mock: handshake, allowed origin, first snapshot, and a second snapshot pushed when another guest joined, applied in place with no console errors. **Not verified live in slice 2:** the alliance socket (verified live in chunk D), reconnect after the server drops (GUT with a fake clock), the Android resume path, and the phone. No visible connection status yet (it would need `en`, `ar` and `fr` strings); chat and report UI are slice 4.
- **Slice 3: base screen, building sheet and upgrades, browser-verified in en and ar (phone check pending).** The shell has a bottom nav bar (Base / Map) and **starts on the base**, which needs only the state, so it shows before the heavy map build; the hidden screen gets no drawing and no input. `BaseView` draws the ground slab and the six sprites on their plots in painter's order with level badges, a progress bar and a dimmed sprite while a building upgrades, and an outline on the selected one; taps hit the painted pixels (alpha >= 40), the nearest building first, and a tap on empty ground closes the sheet. It lives in its own `CanvasLayer` fitted between the HUD and the nav bar (`BaseLayout.fit`), so the map camera is untouched; opening a sheet does not refit. `BuildingPanel` renders a pure `BuildingPanelModel` (level, production, storage, then the running upgrade with bar and countdown, or the next level with cost (lacking resources in red), time, production, the Upgrade button and the blocked reason, or the maximum-level note); it is rebuilt only when the model key, language, background, pending request or notice change, and the countdown ticks in place. The button sends `{"type":"upgrade","building":id}` through `Session.send_intent`; the server's answer (accepted or refused, both carry the base) replaces the state and a refusal's reason is shown under the button. **There is no client prediction:** the button is off while the request is out. When a job's `endsAt` passes, `Session.tick` asks the server for the base (400 ms after, then every 2 s, at most 5 asks per job), so the new level always comes from the server. Counters use `Fmt.amount`. **Ports with golden fixtures from the real code** (`pnpm godot:export`; Vitest fails when stale; only `en` and `ar` are fixtured): `UpgradeView.check` against every `checkUpgrade` outcome (`upgrade-fixtures.json`, fed with the amounts accrued to now, as the counters show them), `BaseLayout` (plots, sprite placement, ground slab, camera fit) and `Fmt` (`formatAmount`, `formatDuration`) against `base-fixtures.json`; the iso-layout formulas were moved out of `BaseScene` into `iso-layout.ts` so the fixtures come from the code the Phaser scene uses. The sprites and their anchors are copied to `art/buildings` and `art/buildings-manifest.json`. French digit groups use U+00A0 because the bundled font has no U+202F. **Verified in the built-in browser** against the mock at phone size: the base, a sheet, a real HQ upgrade (costs deducted, bar, countdown, dimmed sprite, completion picked up from the server), a reload in the middle of a 10-minute upgrade (the bar, the dimmed sprite and the countdown come back from the server's `endsAt`, the M1 "completes correctly after restart" criterion), Arabic RTL (the sheet mirrors, the picture does not), the nav switch to the map. `Loc` has one active background, set by `Session` from the account, so Vietnam's renames (food is rice, the HQ's name) reach the counters and the sheet alike; a second press on Upgrade before the answer sends nothing. **Not in this slice:** training (the barracks sheet has no training section yet), the queue pill and "ask for help" in the HUD, the hero-hall link to the heroes panel, per-building plot art for Vietnam (it reuses the Algerian sprites, as in Phaser). **Not verified:** the phone (touch taps, density), Arabic digits on a device, and a refusal reason shown live (covered by tests only).

4. Rim and an outside mask so decals never float past the map edge. Theme colours from `theme.ts`.
5. Runtime detail overlay (step 1d grain): last, only if the look needs it.

## Server contract for a thin client (checked against `main` 7884d09)

**No server change is needed.** Every snapshot (`GET /v1/state`, intent replies, guest and Google login) already carries what the client needs:

- `state.resources` (stored), `state.levels`, `state.lastUpdated` (epoch ms the amounts are settled to),
- timers as epoch ms: `queue`/`training`/`marches[]` with `startedAt`, `endsAt`, `departAt`, `arriveAt`, `returnAt`,
- `liberations` (server-wide regions held, `from`/`until`), which scale production,
- the server's `now`.

Rates and caps are not sent. They derive from `levels` (and the liberation multiplier), so the client computes them from the exported balance tables. Instead of a server change, drift is caught by golden fixtures: `scripts/export-godot.mjs` runs the real `accrue` over edge cases (cap reached, above-cap kept, time going backwards, ten years offline, liberation starting/ending mid-span, bonus capped) and a GDScript test must reproduce the results from `balance.json` alone. Vitest fails when the committed JSON is stale. **The GDScript half of this check runs locally only (`pnpm godot:test`) until the CI step below is approved**: if someone changes `accrue` and regenerates the fixtures, only the Godot run shows the mismatch.

Client display formula: `ResourceDisplay.amounts` (GDScript) mirrors `accrue`: segments split at liberation changes, `min(cap, stored + rate * multiplier * dt)`, amounts at or above the cap kept as is, `now` from `Clock`: the server's `now` from the last response plus monotonic ticks since (`Time.get_ticks_msec`), so changing the phone's date or time cannot move counters or timers.
